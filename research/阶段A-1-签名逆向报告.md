## 四、Node 实例化：成功，卡点与解法

### 结果
`WebAssembly.instantiate` **一次成功**，无缺失 import。

### 遇到的三个真实卡点（均已解决）

**卡点 1 — wasm 原始导出不能按 JS 语义直接调用**

`exp.qodercontext_prepareInferRequest` 是 wasm 函数，ABI 为 `(retptr, self, ptr, len, ...)`，返回 `void`。
直接 `exp.prepareInferRequest('url', 'body')` 会静默返回 `undefined`（参数错位）。
→ **必须**照抄 wasm-bindgen glue 的包装：先用 `__wbindgen_export2(len, align)` 分配内存、
`__wbindgen_add_to_stack_pointer(-16)` 取返回槽、调用后用 `Mr().getInt32(retptr+n)` 读结果。

**卡点 2 — `QoderContext` 构造参数需要精确的 JSON 结构**

构造签名：`new QoderContext(machineId, cosyVersion, userInfoJson, clientMetadataJson)`

`userInfoJson` 的字段类型由 Rust 侧严格校验，逐次试探得到的正确结构：

```jsonc
{
  "uid": "string",                // 必填
  "encrypt_user_info": "string",  // 由 generate_runtime_auth_fields 产出
  "key": "string",                // 同上
  "organization_id": "string",    // 不能是 null
  "organization_tags": [],        // 必须是数组，不能是 string/null
  "data_policy_agreed": false     // 必须是 boolean，不能是 string/null
}
```

报错依次为：`missing field uid` → `invalid type: null, expected a string` →
`invalid type: string "", expected a sequence` → `invalid type: string "", expected a boolean`。

**卡点 3 — `generate_runtime_auth_fields` 返回 undefined（我自写 glue 的 bug）**

wasm 原始导出需 3 参 `(retptr, ptr, len)`。按 JS 语义传 1 个字符串 → 静默 `undefined`。
→ 补齐包装函数后，正确返回 377 字节 JSON（`encrypt_user_info` + `key`，各 172 字符 base64）。

## 五、签名机制（完整还原）

### 5.1 App 真实调用链

```js
// 1) 初始化上下文（AuthManager.createWasmContext）
let cosyVersion = await getVersion();                    // "1.1.32"
if (!this.machineId) this.machineId = await this.getMachineId();
JlA(this.machineId, cosyVersion, JSON.stringify(this.getUserInfoForAuth()));

// 2) 生成运行期字段（AuthManager.regenerateRuntimeFields）
let A = JSON.stringify({ uid, organization_id, organization_tags, data_policy_agreed });
let e = JSON.parse(fC().generate_runtime_auth_fields(A));
this.cachedUserInfo.encrypt_user_info = e.encrypt_user_info;
this.cachedUserInfo.key = e.key;

// 3) 推理请求签名（A3t 模块的 ner）
function ner(A, e, t, i, n) {          // endpoint, bodyJson, modelKey, modelSource, authManager
  let r = Mc(n => n.prepareInferRequest(A, e, t, i));
  return { url: r.url, headers: vc(r.headers), body: r.body, free: () => r.free() };
}

// 4) 发请求（HDr / sendRemoteChatAsk）
let I = ner(endpoint, bodyJson, modelKey, modelSource, authManager);
let l = await Mo({ operation:"sendRemoteChatAsk", requestClass:"infer-sse",
                   url: I.url, init: { method:"POST", headers: I.headers, body: I.body } });
```

### 5.2 `prepareInferRequest` 实际只吃 2 个参数

实测后 2 个参数**不影响输出**（`t`/`i` 只进 wasm 但未被使用）。它：

- **忽略传入的 path**，URL 硬编码为
  `{endpoint}/algo/api/v2/service/pro/sse/agent_chat_generation?FetchKeys=llm_model_result&AgentId=agent_common&Encode=1`
  （这正是探测报告中「直接请求返回 404」的原因：真实路径带 `/algo` 前缀，且必须签名）
- **加密 body**（`Encode=1` 对应的 Base85 风格密文）
- **返回 20 个签名头**

### 5.3 真正的签名头 ★

`Authorization: Bearer COSY.<base64 payload>.<32位hex签名>`

payload 解码后为：
```json
{"version":"v1","requestId":"<uuid>","info":"<base64 密文>","cosyVersion":"1.1.32","ideVersion":""}
```

完整 20 个头：

| Header | 说明 |
|---|---|
| `Authorization` | **`Bearer COSY.<payload>.<sig>` ← 真正的签名** |
| `Cosy-Key` | base64 密钥材料 |
| `Cosy-Date` | unix 秒时间戳 |
| `Cosy-MachineId` / `Cosy-MachineToken` | 设备标识 |
| `Cosy-User` | uid |
| `Cosy-ClientType` | `6`（QwenWork 集成模式） |
| `Cosy-Business-Product` | `qoder_work` |
| `Cosy-Business-Type` | `agent` |
| `Cosy-Scene` | `assistant` |
| `Cosy-Data-Policy` | `disagree` / `agree` |
| `Cosy-MachineType` | `5` |
| `Cosy-Version` | `1.1.32` |
| `Login-Version` | `v2` |
| `Content-Type` / `Accept` / `Cache-Control` / `Connection` | — |
| `X-Model-Key` / `X-Model-Source` | 由第 3/4 参数注入 |

### 5.4 ⚠️ 最容易踩的坑

**绝不能再用 `Authorization: Bearer <accessToken>` 覆盖 WASM 生成的 `Authorization`。**

这正是本任务前期一直 `403 {"code":"101","message":"Signature invalid"}` 的根因：
签名头本来已正确生成，却被手搓的 Bearer token 覆盖掉了。

```json

      "body":"{\"choices\":[{\"delta\":{\"reasoning_content\":\"Simple\",\"role\":\"assistant\"},\"index\":0}],
```

### 6.3 body 结构（4 种变体实测）

| body 结构 | 结果 |
|---|---|
| `{request_id, session_id, model_config, messages}` 顶层 messages | ✅ 200 |
| 同上，`content` 用 `[{type:'text',text}]` 数组 | ✅ 200 |
| `{request_id, session_id, model: 'pro', messages}` | ✅ 200 |
| `{..., chat:{messages}}` 嵌套 | ❌ `400 messages is required` |

→ **`messages` 必须在顶层**。

## 八、已知限制与风险

1. **依赖 `loginDeviceId` 作为 machineId**。若与 App 实际持久化的 machineId 不一致，签名可能被拒。本环境中二者一致（实测通过）。
2. **`Cosy-Version` 硬编码 `1.1.32`**。App 升级后应从产物版本读取（`COSY_VERSION` 导出 / `X-QwenWork-Version`）。
3. **body 加密与签名黑盒**。签名算法仍在 WASM 内，本方案不解释算法，只复用——因此对版本变更的鲁棒性取决于 WASM 导出名稳定性。若官方更换导出名，需重新定位（本仓库脚本可直接复用）。
4. **未测试多轮会话/工具调用/视觉输入**。当前验证覆盖单轮文本对话。
5. **`organization_tags` / `data_policy_agreed` 恒定传入空值**。企业账号场景需从凭据读取真实值。
6. **headers 返回的是 `Map` 而非普通对象**，必须 `forEach` 展开后再交给 `fetch`（`qwen-signer.mjs` 已处理）。
