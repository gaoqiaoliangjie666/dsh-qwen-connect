# 已知上游边界（2026-09-14 排查记录）

本文件记录**经实测确认属于上游行为、不在插件可控范围**的现象，避免后续重复排查。

## 1. `pro` 模型对高重复度输入会长时间不返回

**现象**：发送「同一字符重复数百次」这类输入时，`pro` 模型可能超过 60 秒不返回首个可用响应。

**实测对照**（同一输入、同一份代码，只换模型）：

| 模型 | 输入 | 结果 |
|---|---|---|
| `pro` | `'重复一遍：' + '测'.repeat(500)` | ❌ 60s 超时 |
| `flash` | 同上 | ✅ 14.1s 正常返回 |
| `pro` | 自然文本 1000 字 | ✅ 5.2s |
| `pro` | 自然文本 3000 字 | ✅ 5.2s |

**判定依据**：**绕开 shim 直连上游**（`curl` 等价路径）复现同样超时；
换成 `flash` 则正常。同一份签名代码、同一个端点，只改 `model` 字段即结果不同
→ 属上游模型行为，插件无从修复。

**结论**：不是缺陷，不修。但据此做了两项加固：

1. 请求体显式给出 `parameters.max_tokens`（32000）——避免模型无上限生成
   （此前完全不发该字段，完全依赖上游默认值）
2. `streamIdleTimeoutMs` 保护——上游长时间无数据时流会超时收尾，不会永久挂起

## 2. 早期「500 字输入超时」的误判

首次排查时用「重复字符」构造长输入，得出「长输入会超时」的结论。
换成自然文本后完全正常（3000 字 5.2 秒）→ **原结论是测试用例本身误导**。

**教训**：构造边界测试用例时，输入形态本身要多样化；
单一形态的输入可能触发特定上游行为，从而把「上游对某类输入的响应」误判成
「我们的实现有缺陷」。

## 3. 复现方式

```bash
# 对照实验（绕开 shim 直连上游）
node research/probes-2026-09-14/verify-max-tokens.mjs
```

判据：若**直连上游**同样超时，则与 shim / 插件无关。
